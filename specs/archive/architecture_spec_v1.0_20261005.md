# LyricNote: iTunes 楽曲解説・和訳・ライナーノーツ付与システム 詳細仕様書 (改訂版 v2.0)

## 1. プロジェクトの目的と目標（Why）

**「言葉の壁を越え、アーティストが楽曲・アルバムに込めた真のメッセージや物語を深く理解し、手持ちの洋楽・邦楽ライブラリでの音楽鑑賞体験を極限まで豊かにすること」**

本ツールは単なる直訳ツールではない。プログレやロックオペラなど、アルバム全体を通したテーマ性や架空のキャラクター、ダブルミーニング・造語などを正確に読み解き、一貫した世界観を持った「和訳」と「ライナーノーツ（アルバム全体解説＋各曲ごとの個別楽曲解説）」を生成・付与することで、ユーザーに深い音楽鑑賞の喜びを提供することを最終目標とする。

---

## 2. 絶対遵守ルール（Safety & Limits）

開発およびシステム稼働において、以下のルールを強制する。

1. **データアクセス制限**:
   - キャッシュ・バックアップ等は指定ディレクトリ（`X:\LylicData`）配下のみに制限。
2. **楽曲ファイルの保護**:
   - `track.Delete()` や `os.remove()` による音楽ファイル（`.m4a`, `.mp3`等）の物理削除・バイナリ改変を絶対禁止。メタデータ更新は iTunes COM API の `Lyrics` プロパティ経由に限定する。
3. **API課金リスクの排除（追加課金ゼロ）**:
   - クラウドLLM (Gemini API) の利用時は、無料枠を超過しないようRate Limitエラーを検知して即時停止する。
   - **手動ハイブリッドモード**: ユーザー加入済みの「AI Proプラン (Gemini Advanced)」をブラウザ経由で活用できるよう、UIに「Gemini用プロンプトのコピー＆出力結果のペースト」機能を実装し、API制限を完全に回避可能とする。
4. **仕様駆動開発（SDD）および検証エビデンスの義務付け**:
   - コード改修前に必ず本仕様書および実行計画を更新・合意する。
   - 修正後は必ず自律テスト・検証を実行し、生ログを伴う検証エビデンス（`TEST_EVIDENCE.md`）を作成・更新した上で報告する。

## 3. インフラ・アクセス設計とセキュリティ要件

### 3.1. 外部公開のセキュリティ評価と実装方針
1. **セキュリティリスク評価**:
   - 本システムはローカルPCのiTunes COM APIおよびファイルシステムにアクセスする権限を持つため、公衆インターネットへの不用意な露出は重大なセキュリティ脅威となる。
   - Gradio Share（`*.gradio.live`）および簡易Basic認証は、レートリミット欠如や総当たり攻撃に対する脆弱性（OWASP非推奨）があるため、**外部公開機能（`--share`）は不採用・完全削除**とする。
2. **安全な接続プロトコル**:
   - サーバーは常にローカルホストまたはLAN向け（`server_name="0.0.0.0"`, `port=7860`）で起動する。
   - 自宅Wi-Fi外（外出先スマートフォン等）から接続する場合は、**Tailscale** 等のエンドツーエンド暗号化メッシュVPN（WireGuard基盤、ゼロトラスト認証）の利用を必須ガイドラインとする。

## 4. アルバム指向アーキテクチャとデータフロー仕様

### 4.1. iTunesライブラリスキャン仕様
- **全曲一括自動スキャン**:
  - 音声トラック（Audioファイル）のみを対象に全件自動スキャン（洋楽/邦楽の選択をユーザーに求めない）。
  - ビデオ、Podcast、PDF等の非音声、および曲名/アーティスト/アルバムが空の不正トラックはスキップ。
  - スキャン時に既存の `track.Lyrics` が存在するかを検知し、DBにキャッシュする。

### 4.2. 音楽評論家（Gemini）と楽曲解説データ構造
- **出力スキーマ（JSON）**:
  Geminiには以下の構造化JSONのみを出力させる。
  ```json
  {
    "is_live": false,
    "album_overview": "アルバム全体の時代背景、テーマ、制作秘話（1000〜2000文字）",
    "story_and_characters": "コンセプトアルバムの世界観・登場人物設定（任意）",
    "track_commentaries": [
      {
        "track_name": "収録曲名（リストと一致）",
        "commentary": "その楽曲独自の解釈、エピソード、歌詞の背景（300〜600文字）"
      }
    ],
    "glossary": [
      {
        "term": "重要な単語・造語・比喩",
        "meaning": "文脈における意味・ダブルミーニング",
        "translation_hint": "和訳のヒント"
      }
    ]
  }
  ```
- **データベース永続化仕様**:
  - アルバム全体解説（`album_overview`）は `albums` テーブルの `liner_notes` に保存。
  - 各曲の個別解説（`track_commentaries`）は、曲名照合（正規化マッチング）を行い、`tracks` テーブルの `liner_notes` カラムに各レコード単位で永続化する。
  - `context_json` は `albums` テーブルに生JSONとして保持する。

### 4.3. 歌詞取得（LRCLIB）の多段階フォールバック仕様
1. **第1優先**: iTunesに既に登録されている歌詞（`has_original_lyrics == 1`）を再利用。
2. **第2優先**: LRCLIB `/api/get` による厳密一致取得（artist, track, album, duration）。
3. **第3優先（フォールバック）**: LRCLIB `/api/search` によるあいまい検索。
   - 邦楽対応のため、クエリ正規化を実施：
     - "THE ALFEE" と "ALFEE" などのプレフィックス吸収
     - "(Live)", "[2012 Remaster]" などの補足表記の除去
     - 全角英数・スペースの正規化
4. **取得失敗時**: 空白のまま放置せず、ステータスを `lyrics_not_found` とし、UIから手動入力可能な状態を維持する。

### 4.4. 翻訳職人（ローカルLLM: gemma2:9b）の安定性・自動スキップ仕様
- **邦楽の自動スキップ**:
  - `language == 'ja'` の楽曲は和訳処理を自動スキップし、翻訳ステータスを `skipped_japanese` とする。
- **洋楽の和訳とVRAM安定化**:
  - `num_ctx` を `4096` に制限し、GPU VRAM不足によるOllamaクラッシュ（WinError 10054 / wsarecv）を防止。
  - 通信エラー時はエクスポネンシャル・バックオフによる自動リトライ（最大3回）を実行。
  - 翻訳メモリ（SHA-256歌詞ハッシュ）により同一曲は即座にキャッシュ適用。

### 4.5. iTunes書き込みと歌詞整形仕様
iTunesの `Lyrics` プロパティへ書き込む最終テキストは、以下の構成とする。

- **洋楽（和訳あり）の場合**:
  ```text
  【Original Lyrics】
  (英語歌詞)

  【和訳】
  (日本語和訳歌詞)

  【楽曲解説: (曲名)】
  (その曲の個別解説)

  【アルバム解説】
  (アルバム全体ライナーノーツ)
  ```

- **邦楽（和訳なし）の場合**:
  ```text
  【歌詞】
  (日本語歌詞)

  【楽曲解説: (曲名)】
  (その曲の個別解説)

  【アルバム解説】
  (アルバム全体ライナーノーツ)
  ```
※ 個別楽曲解説が存在しない場合は「【楽曲解説】」ブロックをスキップし、アルバム解説のみを付与する。
